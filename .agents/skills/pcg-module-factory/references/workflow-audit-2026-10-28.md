# Module skills 修订与 01–03 证据归因

本修订以 main `04952431c8cef913ce1cda0732e98e5231236ff5` 为基础，只改 skills 和参考文档。它不改设计、运行时、Module、参数、质量门槛或历史验证标签，也不表示 01–03 已重新认证。

## 修订原因与处理

| 原问题 | 本次处理 |
| --- | --- |
| 多个 skill 把旧任务的只迁移、不提交、来源排序和暂停状态写成固定权限 | 共用流程先判当前授权与模式；保留实际暂停和设计边界，不由 skill 自动恢复批量任务。 |
| 既有修复、确认设计实现与新生成入口混杂 | 工厂入口分成三种模式；一般迁移适配建议不能覆盖确认设计；新生成仍需当前任务允许。 |
| 合同语义与 schema/消费者支持容易混为一谈 | 核实际导出、参数消费、验证和原生加载；缺口明确记录，不由格式字段宣称功能完成。 |
| 协议默认值、预算和控制 DSL 行为只有零散提醒 | 正式运行前要求记录解析后的协议及 SHA、调用量上界、控制实际接受事件和留出绑定。当前工具尚非全部自动预检，不能称已经自动防错。 |
| 策略失败容易被过早归为设计问题 | 逐类记录协议、观测器、控制、运行时和设计冲突；要求从首个偏离及真实因果取证。 |
| 生产参考保留旧 CLI、连续循环和候选即入库的表述 | 加当前授权和能力核对前提；区分候选记录与正式库资格；历史迭代不再当当前执行计划。 |

以上扰动样本不是人类通关率。可玩见证只证明其具体初态可执行，不能替代鲁棒性资格；策略失败也不证明玩家无解。02/03 的门槛失败是事实，全部失败的首因尚未完成定位，不应把“策略敏感”进一步写成已确定的唯一根因。

技能与流程确有可改善处，但不能用它们替执行失误免责：01 的协议误选由执行者负责；02/03 的控制方案尚未达到目标。原先把02/03笼统列为需要设计审查的表述应收窄为“当前策略未达标，设计冲突未证实”；这是诊断结论的澄清，不撤销旧质量失败或改写旧 raw。后续候选修订须另绑版本与真实证据。
